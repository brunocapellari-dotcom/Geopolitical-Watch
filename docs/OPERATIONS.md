# Operations contract

## Production topology

Canonical production topology:

1. Cloud Run service: private application/API and dashboard shell.
2. Cloud Run Job: registry-driven collection, normalization and consolidated analysis tick.
3. Cloud Scheduler: invokes the single collection/analysis job; the Source Registry controls real per-source cadence.
4. PostgreSQL 18 + PostGIS on Cloud SQL: durable normalized events, entities, claims, episodes, lineage, reports, alerts and operational state.
5. Dedicated VPC + Direct VPC egress + Private Services Access: private database path.
6. Google Cloud Storage: immutable/content-addressed RAW payloads and future static geospatial assets such as PMTiles.
7. Secret Manager: application secret, database password, optional AIS/source credentials.
8. Artifact Registry: immutable scanned production container images.
9. GitHub Workload Identity Federation: keyless deployment identity for already-provisioned production resources.

SQLite and filesystem RAW remain local/test compatibility paths only. Replit and Claude Code are development/review environments, never production state holders.

## Required production settings

Generic/local PostgreSQL deployments may use:

- `GEOWATCH_DB_URL=postgresql://...`
- `GEOWATCH_RAW_BUCKET=<bucket>`
- `GEOWATCH_API_TOKEN=<secret>`

Google Cloud production uses the split Cloud SQL/Secret Manager contract (`GEOWATCH_DB_USER`, `GEOWATCH_DB_NAME`, `GEOWATCH_DB_HOST`, `GEOWATCH_DB_PASSWORD`) generated by Terraform rather than storing one DSN as a canonical secret.

Source credentials remain opt-in and must only be mounted when the corresponding source is enabled. ACLED accepts an issued access token or username/password; AIS requires its provider key before continuous mode is claimed available.

## Health and observability

- `/health` verifies process availability and identifies the selected storage backend.
- `/v2/runtime/readiness` reports production-readiness dependencies without exposing secret values.
- `/v2/source-health` reports source-level health/freshness.
- `/v2/operational` exposes JSON operational counters.
- `/metrics` exposes Prometheus text metrics.
- `/v2/alerts/pending` exposes pending alert payloads through the authenticated API.
- `collector_runs` preserves source-level success/error history and record counts.
- `source_checkpoints` preserves incremental progress.
- `episode_changes` is the durable change lineage.
- `alert_outbox` provides retryable and deduplicated delivery state.

## Product surfaces

- `/dashboard` serves the authenticated MapLibre shell; protected data are fetched from protected API routes at runtime.
- `/v2/map` exposes resolved episode/infrastructure points.
- `/v2/episodes/{episode_id}` provides event, claim, evidence, entity and change-timeline context.
- live aircraft/vessel endpoints keep observed trajectories distinct from inferred/informed route context.
- `/v2/consumers/agrolog/feed` is a read-only filtered consumer view and does not grant another project write access to this database.

## Initial SLO targets

These are engineering targets, not claims about a deployment that has not yet been observed:

- API availability target: 99.5% monthly during the pre-1.0 phase.
- GDELT/GDACS collection freshness target: successful collection within 2 hours.
- Collector failure detection target: surface a source error within one scheduled run.
- RAW durability target: every successfully parsed production payload has a content-addressed GCS object reference.
- Alert dispatch target: queued external notifications are handled by the configured delivery path without changing the source-of-truth event state.
- Database backup target: automated backup plus point-in-time recovery.

## Backup and disaster recovery

Cloud SQL provisioning enables automated backups and point-in-time recovery before sustained collection. RAW objects are content-addressed and use bucket versioning/storage-class transitions according to cost and source-right requirements. A production recovery drill must validate database restore/PITR, API read path, checkpoint integrity, lineage and one controlled collector replay before the deployment is called operationally final.

## Security

- Return the repository to private visibility after the public-Runner bootstrap period, once private Actions billing/capacity is available.
- Never commit API tokens, passwords, webhook secrets, DSNs, Terraform secret tfvars or service-account keys.
- Cloud SQL must have no public IPv4, use private networking and require encrypted transport.
- Production secret payloads use Terraform/provider write-only attributes where supported and live in Secret Manager.
- Runtime identities receive only the database, RAW-bucket and secret permissions required for their task.
- Scheduler receives only permission to invoke its job.
- GitHub deploys through OIDC/WIF and never stores a long-lived Google JSON key.
- External webhook delivery must use HTTPS and authentication where supported.
- Do not expose full copyrighted news bodies in reports or feeds.
- OSINT content remains hostile/untrusted input and never becomes executable instruction.

## Single deployment authority

**Terraform under `infra/gcp/` is the only infrastructure provisioning path.**

The old imperative `gcloud` deployment helper has been retired because it duplicated infrastructure definitions, used a different naming/secret contract and could drift from Terraform. `.github/workflows/gcp-release.yml` only publishes an already-green image to infrastructure that Terraform has provisioned; it is not a second infrastructure-definition system.

Production is considered live only after all of the following are verified against the exact green release commit:

1. Full Project Gate and public-data integration pass on the integrated branch.
2. The same gates pass again on the exact `main` commit.
3. `terraform plan` is reviewed before any apply.
4. Cloud SQL has only private IP, encrypted connectivity, PostGIS and expected schema.
5. GCS RAW object is written by an actual scheduled/source execution.
6. Manual Cloud Run Job exits successfully.
7. `/health`, readiness, source-health, episode/map/live routes and metrics return expected authenticated responses.
8. Cloud Scheduler triggers at least one successful job.
9. Production container digest matches the scanned release image.
10. Backup/PITR is enabled and an actual restore drill succeeds.
11. Optional continuous AIS is only marked ready after a valid key and intentionally enabled always-on compute.

Until these checks occur, the repository is deployment-ready but not a verified 24/7 production deployment.
